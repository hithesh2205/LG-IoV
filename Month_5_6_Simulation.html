SERVER PLAINTEXT ACCESS — individual updates 0 · aggregates only
Month 5–6 progress · interactive walkthrough

A vehicle fleet that learns to spot intrusions — without anyone seeing the data.

Each vehicle trains a local intrusion detector on its own CAN / V2X traffic, encrypts the model update, and sends it to a server that combines the updates without ever decrypting a single one. This page walks through every piece we have built so far.

01 · The deadlock this project breaks

Three facts that pull against each other

Any two of these are easy. All three at once is the problem the project exists to solve.

FACT 1

Raw logs can't leave the vehicle

CAN traffic, GPS position and driving behaviour identify a driver's routes and habits. Pooling them to a central server is off the table.

FACT 2

Sharing the model update isn't safe either

Federated learning shares a 44,164-number update instead of data — but those numbers can be inverted back into training samples. They must be encrypted end to end.

FACT 3 → OUR FIX

Encryption blinds the server to attackers

Once updates are encrypted the server can't tell a helpful vehicle from one feeding poison. We score each vehicle by distance to the shared model — computable on the ciphertext — and down-weight outliers without decrypting them.

03 · CKKS in real numbers

How the server adds numbers it cannot read

A miniature version of the encryption scheme. Change the three vehicle weights and watch the server recover their average from ciphertext alone.

Three vehicle weights

use production-grade parameters (larger modulus, smaller noise)

Encryption of a weight w:  b = −(a·s) + Δ·w + e (mod q); ciphertext = (a, b). Homomorphic add = add the ciphertext parts. Decrypt = (b + a·s) mod q, then ÷ Δ. The real system packs 4,096 weights into each ciphertext and its numerical error is around 10⁻⁸.

04 · Encryption is accuracy-free

The encrypted model scores the same as the plaintext one

Real CKKS on one arm, exact plaintext on the other, everything else held identical. 3 seeds · 10 vehicles · 5 rounds. The near-equal bars are the result.

The gap between the two bars is smaller than the run-to-run variation from the random seed on every dataset. CKKS adds numerical error around 1×10⁻⁸ — six orders of magnitude below the noise already in stochastic gradient descent.

06 · Can it run over a vehicle network?

The honest bottleneck is bandwidth, not speed

Encryption time is fine — about 42 ms to encrypt an update, ~120 ms for the encrypted outlier score. The size is the problem.

plaintext update0.17 MB
naive CKKS3.51 MB
packed — shipped2.47 MB
One vehicle's encrypted update is 2.47 MB — about 915 DSRC frames (2.7 KB each).
Our packing module cut it 29.6% with zero accuracy cost by dropping one unused precision level before transmit.
A 50-vehicle round still moves ~180 MB. It does not fit a V2X budget.
Next lever: roadside units pre-aggregate so only one ciphertext per unit reaches the server — an architecture decision to take early.
07 · Where we are on the 12-month plan

Months 1–5 delivered; the aggregator is running early

The cryptography and machine-learning tracks are on or ahead of schedule. The remaining gap is on-vehicle deployment, which begins after the OpenFHE C++ migration.

Month 6 priorities

  1. OpenFHE migration — turns the modelled multi-key layer into real threshold cryptography, and gives the C++ core the on-vehicle port needs.
  2. Two one-line security fixes — bind the round number into the message tag (replay), enforce noise flooding in the deployment profile.
  3. Patient-attacker experiment — test the known blind spot: small, consistent, biased updates over many rounds.
  4. Scale 10 → 50 vehicles toward the roadmap target.
  5. Re-acquire VeReMi with sender IDs so the misbehaviour task can be expressed.
