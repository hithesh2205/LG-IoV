    00 · Framing

    Three vehicles never show their weights in the clear.

    FedIoV's server only ever aggregates ciphertexts. Every worked number on the next few pages is taken directly from the project's own derivation — the same toy example, walked forward one operation at a time, then connected to what genuinely happens when the real TenSEAL CKKS library runs on your actual 44K-parameter ChebyKAN layers.

    The shape of the argument

    • Steps 1–4 — the simplified single-key CKKS toy example (secret key [4, 9], three clients), encrypted, aggregated, and decrypted by hand.

    02 · Client-side encryption Simulated

    Each vehicle scales, masks, and ships a ciphertext.

    b = a·S + e + Δ·PT  (mod q)

    a is a fresh random vector the client draws every time (safe to publish). e is small random noise. Neither the server nor any other client ever learns S.

    Client 1 0.10
    a₁[37, 52]
    e₁5
    b₁ = 37·4+52·9+5+100721
    CT₁ = ([37, 52], 721)
    Client 2 0.12
    a₂[21, 66]
    e₂3
    b₂801
    CT₂ = ([21, 66], 801)
    Client 3 0.09
    a₃[58, 14]
    e₃4
    b₃452
    CT₃ = ([58, 14], 452)

    Every ciphertext leaving a vehicle looks like uniform noise to anyone without S — including the aggregation server.

    03 · Server-side aggregation Simulated

    The server adds ciphertexts. It never decrypts anything.

    CKKS is additively homomorphic: adding ciphertexts is the same as adding the messages inside them, so plain vector addition across the three (a, b) pairs is a legal FedAvg sum — done entirely on encrypted values.

    ciphertext-only summation
    a_sum = a₁ + a₂ + a₃ = [37,52]+[21,66]+[58,14]
    b_sum = b₁ + b₂ + b₃ = 721+801+452
    a_sum
    [116, 132]
    b_sum
    1,974

    That 0.004 gap is encryption noise, not a bug — a side effect of the toy example's small modulus (q = 100,003). Real CKKS runs with a modulus many orders of magnitude larger, which is exactly why the measured error in step 6 is ~10⁻⁸ instead of ~10⁻².

    05 · From toy integers to polynomial rings

    Production CKKS runs this same shape of math over polynomials.

    Swap the integer secret key for a secret polynomial, and every step above still holds — encryption is still "mask with randomness," aggregation is still "add," decryption is still "unmask with the secret."

    Keys, in the ring R_q = Z_q[x] / (xⁿ+1)
    s(x) ∈ R_q  secret key polynomial
    a(x)  random public polynomial
    e(x)  error, lower degree
    b(x) = −a(x)·s(x) + e(x)

    Public key = (a, b). Anyone can encrypt with it; only the holder of s(x) can decrypt.

    Encrypting a plaintext polynomial
    m(x) = 288 + 325x + 471x²  (×Δ)
    u(x), e₁(x), e₂(x)  fresh randomness
    c₀ = b·u + e₁ + m
    c₁ = a·u + e₂

    Ciphertext = (c₀, c₁). Decrypt with m'(x) = c₀ + c₁·s, then divide by Δ.

    A weight tensor is just the coefficient list of m(x) — this is why one ciphertext can carry thousands of weights at once (see the "slot count" in step 6).

    07 · Why single-key CKKS is the wrong trust model for a fleet

    One shared secret key means one leaked key breaks every vehicle.

    Steps 1–6 all share a single secret key S across every client — standard for TenSEAL/SEAL, which is single-key only. For independently-owned vehicles, that's a single point of failure: any one compromised car can decrypt every other car's updates. The fix is to never let any one party hold the whole key.

    Splitting S = [4, 9] across two independent key-custodians

    Off by 5× and meaningless — a lone key-share reveals nothing usable about the plaintext.

    A terminology note worth being precise about in front of your guides: what's shown above is threshold / multiparty CKKS — one shared public key, secret key split into shares, decryption needs a quorum of shares. This is what's practically deployed today (e.g. the dckks package in the Lattigo library) and is a straightforward extension of everything in steps 1–6.

    "True" multi-key CKKS is a different, heavier construction: every client keeps a fully independent key, ciphertexts from different keys are algebraically extended (dimension grows with the number of keys) before they can be combined, with its own key-switching and noise-growth analysis. It's an active research area and not something TenSEAL/SEAL support out of the box — worth flagging as future work rather than implementing under time pressure.
