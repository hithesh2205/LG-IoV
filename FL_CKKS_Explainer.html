What happens to a weight?

Follow four numbers from the moment the server creates them, out to five vehicles, through encryption, back into an aggregate nobody could read on the way, and around again. No prior knowledge assumed.

01 · why this is hard

Three rules that fight each other

Satisfy any two and the problem is easy. All three at once is the project.

Rule 1 · data stays home

🚗 ✋ ☁️

CAN traffic and GPS reveal a driver's routes and habits. Raw logs can never be uploaded — so the fleet cannot simply pool its data and train one strong detector.

Rule 2 · the update leaks too

📊 → 🚗

Federated learning sends a 44,164-number model update instead of data. But those numbers can be run backwards to reconstruct the training samples. So the update must be encrypted too.

Rule 3 · encryption blinds the referee

🔒 🙈 ⚠️

Once every update is sealed, the server cannot tell a helpful vehicle from one feeding it poison. Solving that without ever unsealing anything is the core of this work.

the whole deck in one line Five vehicles will train, seal, send, be scored while still sealed, be combined while still sealed — and only the combined result is ever opened.
raw data · never leaves the vehicle update · must be sealed sealed updates · cannot be checked the normal way

07 · inside the server

What the server actually holds

This slide is the entire privacy claim. Left: what it would love to have. Right: what it really has.

the server does NOT have

W₁ = [0.24, −0.08, 0.39, 0.47] W₂ = [0.22, −0.12, 0.37, 0.52] W₃ = [0.26, −0.09, 0.36, 0.49] W₄ = [0.23, −0.11, 0.40, 0.48] W₅ = [0.25, −0.10, 0.38, 0.51]

It has no key that opens any one of these, and never will. Not "it promises not to look" — it mathematically cannot.

the server DOES have

🔒 C₁ = (c₀¹, c₁¹)  8f3a…c02e 41bd…97f5 🔒 C₂ = (c₀², c₁²)  2e91…7d44 ba05…3fc8 🔒 C₃ = (c₀³, c₁³)  d47c…5a13 90ef…21ab 🔒 C₄ = (c₀⁴, c₁⁴)  61b8…ee07 3c2d…d95f 🔒 C₅ = (c₀⁵, c₁⁵)  a30f…4b6c 7e51…08d2

Five pairs of polynomials. To the server these are indistinguishable from random numbers — and it must now decide which of them to trust.

this is checked, not asserted A counter in the code increments on every decryption of an individual update, and the run aborts if it is ever non-zero. Across all four datasets × 5 rounds it has stayed at 0.

08 · the referee problem

The standard defence stops working here

Multi-Krum is the textbook way to spot a poisoning client. On sealed data it breaks — and understanding exactly why explains our whole design.

Multi-Krum, normally

client updates
↓ pairwise distances
↓ rank them
↓ pick the smallest
↓ drop the rest
↓ average survivors

what sealed data allows

✓ add two ciphertexts
✓ subtract
✓ multiply by a number
✓ multiply two ciphertexts
✗ compare two values
✗ sort / rank
✗ pick the smallest

so Multi-Krum cannot run

Its middle three steps are all comparison. Arithmetic survives encryption; decisions do not.

Our Month-4 code "solved" this by decrypting every client's update to run the comparison — which destroyed the exact property the project exists for. That was defect D4, and fixing it is what Month 5 was about.

the reframe that unlocks it Don't ask "which client is furthest from the other clients" — that needs everyone's plaintext. Ask "how far is this client from the model we already published?" — and the server already holds that model in the clear.
arithmetic on ciphertext · works comparison / ranking · impossible therefore · change the question
09 · FheFL scoring · the real formula

Scoring every vehicle without opening any of them

Distance is measured against W⁽⁰⁾, which the server has in plaintext. That makes the whole calculation possible on sealed data.

step 1 · encrypted distance to the published model  (FheFL eq. 11)

[d ᵘ] = gᵀg + [ (f ᵘ − 2g)ᵀ · f ᵘ ]

g = W⁽⁰⁾, plaintext at the server  ·  f ᵘ = that vehicle's sealed update. Every operation is add / multiply, so it runs entirely on ciphertext. Measured cost: 18 ms per ciphertext.

step 2 · turn distance into trust  (eq. 7)

p ᵘ = 1 − d ᵘ ⁄ Σⱼ d ʲ   so that Σ p = U − 1 = 4

Far from the published model → small weight. Close to it → large weight. Nobody is thrown away, unlike Multi-Krum — a vehicle that met a genuinely new attack is the most valuable update in the round.

the one thing the server does learn To compute p it must see the distance numbers — 5 scalars per round, against 44,164 hidden parameters. That is the measured, quantified privacy cost of this design, and it is stated in every report rather than glossed over. A stricter mode that hides even these is specified and costed, but not yet built.

Combining five sealed models into one

The server now does arithmetic on data it cannot read. Nothing is opened at any point on this slide.

the simple idea first — a plain average

Enc(W₁) + Enc(W₂) + … + Enc(W₅)
= Enc(W₁ + W₂ + … + W₅)
× 1/5 → Enc( mean )

Add the sealed blocks; the seal survives, and what is inside has been added too. This is the whole magic of homomorphic encryption in one line.

what actually runs — trust-weighted, not a plain average

Enc(Wᴳ¹) = Σᵤ pᵘ · Enc(Wᵤ)

A plain 1/5 average is just this formula when every vehicle is equally trusted. The scores from the previous slide slot straight in — multiplying a ciphertext by a plain number is allowed.

why the server can open the sum but never one vehicle

each vehicle holds a share of the key:   s = s₁ + s₂ + s₃ + s₄ + s₅
vehicles mask their share in pairs:   ssᵤ = sᵤ + Σj≠u su,j
the masks are equal and opposite, so they cancel only in the total

The server can assemble a key that opens the aggregate, and no key that opens any individual. To unmask one honest vehicle it would have to collude with all four others.

Math details

Deliberately kept out of the main flow. None of this is needed to follow the story.

the ring
R_q = Z_q[x] / (x^N + 1)  N = 8192

All values are polynomials of degree < N with integer coefficients mod q. Our chain is [60, 40, 40, 60] bits = 200 bits total, giving 128-bit security and 2 multiplication levels.

encode
real vector → ×Δ → integer polynomial
Δ = 2⁴⁰   slots = N/2 = 4096

4,096 real numbers pack into one ciphertext, so 44,164 parameters need 11 ciphertexts — not 44,164. This packing is what makes the scheme affordable at all.

encrypt / decrypt
b = −a·s + e  (public key = (a,b))
c₀ = b·u + e₁ + m  c₁ = a·u + e₂
m′ = c₀ + c₁·s  then ÷ Δ

Security rests on Ring-LWE: recovering s from b = a·s + e is believed hard even for quantum computers. Removing e would make it trivial linear algebra.

noise and depth
each ct×ct multiply consumes one level

A chain of L primes allows L−2 multiplications. Run out and the ciphertext no longer decrypts. Homomorphic addition costs ~0.03 ms; ciphertext×ciphertext costs ~15 ms — a 490× gap, which is why the protocol is designed to need as few multiplies as possible.

FheFL scoring, exact
[dᵘ] = gᵀg + [(fᵘ − 2g)ᵀ·fᵘ]  (eq. 11)
pᵘ = 1 − dᵘ / Σⱼ dʲ  (eq. 7)  Σpᵘ = U−1
gᵢ = (1/(U−1)) Σᵤ pᵘ · fᵘ  (eq. 9)

Source: Rahulamathavan et al., arXiv:2306.05112. Implemented in federated/server.py :: aggregate_round.

multi-key sharing
s = Σᵤ sᵤ  ssᵤ = sᵤ + Σ_{j≠u} s_{u,j}
s_{i,j} = −s_{j,i} ⟹ Σᵤ ssᵤ = s

Masks cancel only in the total, so the server assembles a key for the aggregate and none for an individual. Recovering one honest vehicle requires colluding with U−1 others. Our addition to the paper: masks are re-derived per round for whoever actually reported, so a vehicle in a tunnel no longer corrupts decryption.

the honest boundary

The CKKS arithmetic is real (TenSEAL). The multi-key key management is an algebraic model, because TenSEAL exposes no multi-key API. OpenFHE was selected to replace it and that migration is the Month-6 priority. Until it lands, nothing here should be described as "full multi-key CKKS".
